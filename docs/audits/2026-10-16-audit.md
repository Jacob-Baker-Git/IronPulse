## Findings

### F1 — critical — Upload keystore and its passwords are public

`ironpulse-upload.keystore` and `keystore.properties` (store password, key
alias, key password) have been tracked since the initial commit `e8e49f7`
(2026-06-11), and `github.com/Jacob-Baker-Git/IronPulse` is **public**.
`.gitignore` only ignores `*.png` and build output, although the comment in
`app/build.gradle` says to keep both out of version control.

Anyone can sign an APK/AAB as the IronPulse upload key holder.

Fix, in this order:
1. If the app is on Play with Play App Signing: request an **upload key reset**
   in Play Console (Setup → App integrity) and generate a new upload key. The
   app-signing key Google holds is not exposed.
2. Add `*.keystore`, `*.jks`, `keystore.properties` and `local.properties` to
   `.gitignore`; `git rm --cached` all three.
3. Optionally purge history (`git filter-repo`) and force-push — but treat the
   old key as burned regardless; clones and forks keep it.

`local.properties` is also tracked (only an SDK path, harmless but noise).

### F2 — high — A failed or partial import leaves a mix of old and new data

`MoreFragment.importData` writes each zip entry straight over the live file,
non-atomically, on the UI thread:
- If the zip breaks part-way, earlier files are already overwritten, the user
  sees "Import failed", and the next `saveAsync()` from the still-live old
  repository writes the old in-memory data back over some files. Result: a
  blend of both.
- Files absent from the backup (an older backup without `foodlog.json` or
  `achievements.json`) are left in place, so "replaces your current data" is
  not true.
- A file that parses badly is later **deleted** by `loadJson` (see F4).

Fix: extract to a temp dir, parse every file with the same Gson types, and
only then swap them in (delete files missing from the backup). Drain the old
repo first: cancel `pendingSave` and wait for `ioExecutor` before
`invalidate()`, or a queued save from the old instance can overwrite the
imported files.

### F3 — medium — `|` in an exercise name loses that day's completions

`completed.json` stores each completion as `name|addedDate|weight|reps|rest|id`
and nothing strips `|` from names (add dialog `WorkoutFragment:617`, rename,
custom templates). On the next launch, `LocalDate.parse(parts[1])` throws and
the outer catch at `AppRepository.java:294` drops **every** completion for that
date — the streak and history change silently. Custom split templates use the
same separator.

Fix: strip or reject `|` at the three name inputs (one shared helper), or store
completions as Gson objects instead of pipe strings.

### F4 — medium — Corrupt-JSON handling deletes the user's data

`loadJson` deletes a file on `JsonSyntaxException`. With atomic writes the
app shouldn't produce bad JSON itself, so the realistic sources are an import
(F2) or a future model change — and in both cases deleting is the worst choice.

Fix: rename to `<file>.corrupt` instead of `delete()`.

### F5 — medium — "Rest over" alert only fires if the process is still alive

`RestTimerState` is static memory. `RestAlarmReceiver` returns early when
`endsAt() == 0`, which is what a fresh process sees after Android has killed
the backgrounded app — the exact case the alarm exists for. The live
countdown notification still shows, but the audible alert and its Log-set
action never arrive.

Fix: put the end timestamp in the alarm intent extras and check that instead
(the cancel path already uses a fixed request code, so stale alarms are still
cancellable).

### F6 — medium — Widget refresh runs on the save thread against live lists

`saveAsync` calls `WorkoutWidgetProvider.updateAll` on `ioExecutor`, which
walks `repo.exercises` / `repo.completed` while the UI thread may be mutating
them. Any `ConcurrentModificationException` is swallowed, so the widget just
goes stale sometimes. After an import, `AppRepository.get()` (unsynchronised)
can also be reached from this thread while the instance is null, building a
second repository in parallel with the main thread's.

Fix: post `updateAll` to the main handler instead of running it on the
executor.

### F7 — low — "Clear All Data" leaves state behind

`clearAll()` doesn't reset `heightCm`, `useLbs`, `darkMode` or the reminder
fields, doesn't cancel the reminder alarm, doesn't re-seed the five default PR
rows (that only happens in `load()`), and doesn't refresh the widget or the
open screens. A pending `saveAsync` queued just before can also rewrite the
files right after they're deleted.

### F8 — low — Smaller correctness and copy items

- Records match lifts by name, but `renameExercise` doesn't rename the matching
  `RecordData`, so auto-PR detection stops after a rename.
- `SetLog`s are keyed by exercise name, so two exercises with the same name
  share set history and quick-log counts.
- Settings still says "Exercise schedule: Every 7 days from added date" —
  out of date since multi-day plans.
- README: "the only way data leaves the phone is a backup file the user
  exports" — `allowBackup="true"` with `<cloud-backup/>` also sends it to the
  user's Google Drive. The privacy policy already says this; the README doesn't.
- No `gradlew`/`gradlew.bat` committed, so a fresh clone can't build from the
  command line.
